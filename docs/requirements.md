- 版：0.4
- 作成日：2026-11-21
- 前作：Sip Notes（https://github.com/0tsu-0w0/drink-note）

## 1. 背景と目的

### 1.1 背景
前作 Sip Notes は記録できる項目が充実していた一方で、使いにくさから定着しなかった。
コードの調査と利用者ヒアリングから、離脱の原因は次の6つが重なったものと判断した。

| # | 離脱理由（ヒアリング） | 前作の具体的な原因 |
| :-- | :-- | :-- |
| 1 | 入力項目が多く面倒 | 記録フォーム1画面に、素性5〜7欄・フレーバーのチップ50個超・評価軸8項目などがすべて同じ重さで並んでいた。前回の内容を引き継げず、カテゴリを切り替えると入力内容が消えた |
| 2 | 開くまでが遠い | メール確認つきの登録が必要で、PWAにも対応していなかった（ホーム画面から起動できない） |
| 3 | 記録しても見返さない | 保存後は一覧に戻るだけ。ふりかえり画面は別の場所にあった |
| 4 | 単純に忘れる | 通知や連続記録の表示など、記録を思い出すきっかけがなかった |
| 5 | ジャンルが全部ひとまとめ | コーヒー・お茶・お酒の13カテゴリが1列に並び、フォームも一覧も共通だった |
| 6 | UIがわかりにくい | 書体が4種類混在、文字10〜11px・ボタンの上下余白2pxと小さすぎた。「一杯を記す」「素性」「ふりかえり」など、意味がすぐ分からない言葉が多かった |

### 1.2 目的
**「いつもの一杯なら10秒で残せて、続けたくなる」飲み物ログ**を作る。
普段は最小限の入力で済ませ、気が向いたときだけ詳しく書けるようにする。

### 1.3 成功指標
| 指標 | 目標 |
| :-- | :-- |
| 候補から記録するときの所要時間（中央値） | 10秒以内 |
| 新しい銘柄をかんたん記録するときの所要時間（中央値） | 30秒以内 |
| 4週間後の継続率（登録から22〜28日目に1件以上記録した人の割合） | 40%以上 |
| 継続している人の週あたり記録数 | 3件以上 |

計測方法：継続率と記録数は drinks テーブルから集計する。所要時間は、記録画面を開いてから保存するまでの秒数を記録ごとに保存して集計する（6章 `entry_seconds`）。外部の解析サービスは使わない。

## 2. 対象ユーザーと利用シーン

- **対象**：本人と、本人がアプリを配る友人・知人。一般公開して不特定多数に配る想定はしない。
- **端末**：主にスマホ（iPhone / Android）。PCのブラウザでも使える。
- **主な利用シーン**
  1. 自宅や職場でいつものコーヒーを飲んだ → 候補から1タップで記録
  2. カフェで初めての一杯を飲んだ → 名前・★・ひとことを記録
  3. 気になる日本酒やワインを飲んだ → 「詳しく書く」を開いて、産地・フレーバー・合わせた料理まで残す
  4. 店で「前に飲んだあれ、何だっけ」となった → 履歴を検索する
  5. 気に入った一杯を友人に見せる → 共有URLを送る

## 3. スコープ

| 区分 | 内容 |
| :-- | :-- |
| **MVP（第1段階）** | Googleログイン／Appleログインの仕組み（無効の状態で組み込み）／カフェ・お酒タブ／かんたん記録と詳しく書く／前回の内容の再利用／保存直後のフィードバック／履歴と検索／今週のまとめ／編集・削除／PWA（ホーム画面への追加） |
| **第2段階** | Appleログインの有効化（Apple Developer Program 登録後）／リマインド通知／連続記録の表示／ペアリング／共有URL（OGP画像つき） |
| **後回し** | 写真の添付／データの書き出し（CSV） |
| **対象外** | 前作のデータ移行／日本茶の種類／評価軸・SCAJ採点／メール＋パスワードでのログイン／パスワード再設定／SNS的な機能（フォロー・タイムライン） |

### 4.2 ジャンルと種類
記録は「カフェ」と「お酒」の2ジャンルに分け、タブで切り替える。各ジャンルのタブには、そのジャンルの記録・候補・まとめだけを出す。「履歴」タブは全ジャンルをまとめて表示し、ジャンルで絞り込める。

| ジャンル | 種類（最初の画面で選ぶ） | 細かい種類（詳しく書くで選ぶ・任意） |
| :-- | :-- | :-- |
| カフェ | コーヒー／紅茶／その他 | コーヒー：ドリップ・エスプレッソ・ラテ・水出しなど。紅茶：ストレート・ミルクなど。日本茶などは「その他」で名前に書く |
| お酒 | ビール／日本酒／ワイン／ウイスキー／焼酎／サワー・チューハイ／カクテル／その他 | ワイン：赤・白・ロゼ・スパークリング。ビール：ラガー・IPAなど。ほかも前作の分類から絞って引き継ぐ |

| ID | 要件 | 優先度 |

| F-12 | 種類を選び直しても、入力済みの名前・★・メモは消えない | M |

## 6. データ要件（論理モデル）

**profiles**（利用者）
- id、表示名、最後に使ったタブ、通知時刻、作成日時

**drinks**（1杯分の記録）
| 項目 | 型 | 必須 | 備考 |
| :-- | :-- | :-- | :-- |
| id | uuid | ○ | |
| user_id | uuid | ○ | |
| genre | `cafe` / `alcohol` | ○ | |
| kind | text | ○ | coffee、beer など（4.2の種類）。genre と矛盾する組み合わせはDBの制約で弾く |
| sub_kind | text | | ドリップ、赤 など |
| name | text | ○ | 1〜100文字 |
| name_key | text | ○ | 名前を表記ゆれ吸収のため正規化した値（NFKC正規化・空白除去・小文字化）。同じ銘柄の集計に使う |
| rating | 1〜5 | | |
| memo | text | | 500文字まで |
| flavors | text[] | | |
| origin / maker / place | text | | |
| abv | numeric | | お酒のみ |
| drank_at | timestamptz | ○ | 飲んだ日時 |
| visibility | `private` / `unlisted` | ○ | 初期値 private |
| hide_place | bool | ○ | 共有時に場所を隠す |
| entry_seconds | integer | | 記録画面を開いてから保存までの秒数（成功指標の計測用）。編集時は更新しない |
| client_id | uuid | ○ | 端末側で採番するID。オフラインで記録したものを再送したとき、二重登録を防ぐ |
| created_at / updated_at | timestamptz | ○ | |

**pairings**（第2段階）
- id、drink_id、名前、★。飲み物の記録を消すと一緒に消える

**flavor_words**（自分で追加したフレーバーの言葉）
- user_id、genre、言葉

前作との主な違い：
- 産地などを JSON にまとめず、**決まった列**に分けた（検索しやすくするため）。
- ペアリングを別の記録として持たず、**飲み物の記録に子として紐づけた**。
- 評価軸（axes）はなくした。

## 7. 非機能要件

| 分類 | 要件 |
| :-- | :-- |
| 性能 | ホーム画面のアイコンを押してから記録画面を開けるまで2秒以内（4G回線想定）。保存ボタンを押したら即座に完了表示を出し、通信は裏で行う |
| PWA | ホーム画面に追加でき、ブラウザの枠なしで起動する。オフラインでも記録でき、つながったときに送信する |
| 対応環境 | iOS Safari 16.4以上、Android Chrome、PC版の Chrome / Safari / Edge の最新版。iOSの通知はホーム画面に追加した場合のみ使える（OSの制約） |
| アクセシビリティ | 本文16px以上、押せる部分は44×44px以上、文字と背景のコントラスト比4.5:1以上。ライト／ダークの両方に対応 |
| セキュリティ | Supabase の行レベルセキュリティ（RLS）で、自分の記録だけを読み書きできるようにする。共有ページは公開設定にした記録だけを返す。service_role キーはブラウザに渡すコードと公開リポジトリに置かない。アカウント削除（認証ユーザーの削除には管理者権限が要る）はサーバー側だけで実行する |
| 運用 | 運用の手間をかけない。メール送信（SMTP）を使わない。Supabase の無料プランは7日ほどアクセスがないと休止するため、前作と同じく1日1回の定期アクセス（Vercel Cron）で休止を防ぐ |
| 費用 | 月0円で運用できる範囲（Vercel と Supabase の無料プラン）。Appleログインを使う場合のみ Apple Developer Program の年会費（99USD）がかかる |

## 8. UI/UXガイドライン

1. **書体は1種類**（システムフォント）。数字だけ等幅にしてよい
2. **言葉は短く具体的に**：「記録する」「保存」「履歴」「まとめ」「お店・産地」。雰囲気だけの言葉や、説明的な長い文は使わない
3. **説明文は置かない**。使えば分かる作りにし、必要なら入力欄のプレースホルダーで伝える
4. **主な操作は画面下半分で行う**（片手の親指で届く位置）。「＋」ボタンと保存ボタンは大きくする
5. **初期表示は最小限**にし、それ以外は「詳しく書く」で開く
6. **色は2つだけ**：カフェは茶系、お酒はワインレッド系。それ以外は無彩色にする
7. **確認ダイアログを出さない**。削除なども即実行し、「元に戻す」で取り消せるようにする。例外はアカウント削除だけ
8. **アカウント関連のメニューは設定画面にまとめる**。ヘッダーには置かない

## 11. リスク

| # | リスク | 影響 | 対策 |
| :-- | :-- | :-- | :-- |
| R-1 | iPhoneでホーム画面から起動したPWAでは、Google・Appleのログイン画面がSafariで開き、ログイン状態がPWA側に戻らないことがある | 開くまでが遠い問題が再発する | 技術設計の最初に実機で検証する。戻らない場合は、PWAの中でログインを完結させる方式に切り替える |
| R-2 | オフライン記録（端末に一時保存して後で送る）は、同期・二重登録・編集の衝突を扱う必要があり、MVPの中で最も実装が重い | MVPの完成が遅れる | `client_id` で二重登録を防ぐ。MVPでは「オフライン中は新規記録だけ受け付ける」に絞ることも検討する（Q-7） |
| R-3 | Appleログインは Apple Developer Program に登録するまで動作確認ができない | 有効化したときに不具合が見つかる | 登録後に有効化する前に、実機での確認手順を用意しておく |
| R-4 | Googleログインを本番公開するには、アプリ名・ロゴ・プライバシーポリシーのURLを Google に登録する必要がある | 公開直前に作業が詰まる | F-05 のページをMVPで作る。Google への登録はアプリ名が決まってから行う |
